\chapter{Implementation and Methodology}

\section{Implementation Goals}

The implementation part of this thesis was designed as an experimental and
educational tool for studying the Merkle--Hellman knapsack cryptosystem. Its
main goal is to demonstrate the complete workflow of the scheme: key
generation, encryption, decryption, and verification of the recovered
plaintext. The implementation also includes a permuted variant, which makes it
possible to compare the basic construction with a simple modification of the
public key structure.

The program is not intended to be a secure cryptographic library. The schemes
studied in this thesis are historically important, but they are known to be
insecure against cryptanalytic attacks. For this reason, the implementation is
used mainly to illustrate how the trapdoor construction works in practice and
to support the theoretical discussion from the previous chapters.

A further goal is to provide a basis for simple cryptanalytic experiments. The
implemented attacks are meant to be illustrative rather than complete
state-of-the-art cryptanalysis. They are used to show that small or structured
knapsack instances can be attacked directly, and to connect the implementation
with the theoretical discussion of weaknesses in the Merkle--Hellman scheme and
its variants.

Another goal was to prepare a simple environment for experiments. The
program supports deterministic initialization through explicit seeds, so the
same keys and test cases can be reproduced across multiple runs. This is useful
for debugging, correctness testing, and later benchmarking of parameters such
as block length, key size, ciphertext size, and running time.

\section{Choice of Programming Language and Libraries}

The implementation was written in the C programming language for practical
reasons connected with the experimental nature of the work. The program has to
store and manipulate sequences of private weights, public weights, moduli,
multipliers, ciphertexts, and intermediate values. C made it possible to keep
these data structures explicit and to control how keys, messages, and
scheme-specific objects are initialized, reused, and cleared during experiments.

A major requirement of the implementation is support for integers larger than
those provided by the standard C integer types. In knapsack cryptosystems, the
weights, modulus, multiplier, and ciphertexts can grow quickly as the block
length increases. For this reason, the implementation uses the GNU Multiple
Precision Arithmetic Library (GMP). GMP is used for arbitrary-precision integer
arithmetic, including additions, comparisons, modular multiplication, modular
reduction, modular inversion, and ciphertext computation. This made it possible
to keep the implementation in C while supporting arithmetic beyond standard
64-bit limits.

Seed handling was implemented explicitly in order to support both reproducible
and non-deterministic experiments. The program uses a pseudo-random generator
initialized either from a user-provided seed or from operating-system entropy.
A provided seed makes experiments exactly repeatable, while the entropy-based
mode allows non-deterministic runs. If system entropy is unavailable,
initialization fails rather than silently falling back to a weaker source;
deterministic execution is still possible by providing an explicit seed.

The build process is controlled by a simple Makefile. It supports separate
debug and release builds, as well as an address-sanitized configuration for
runtime checking. This was useful during development, because the code uses
dynamic allocation for keys, messages, ciphertexts, and scheme-specific
internal structures. The toolchain was kept simple so that the program could be
built and tested in both macOS and Linux environments with only a C compiler,
Make, and GMP installed.

\section{Program Architecture}

The implementation was organized as a small modular C program. The main goal
was to keep the cryptographic code separate from user interaction, input
parsing, and benchmarking. This made the program easier to test and also made
it possible to add new knapsack variants without changing the rest of the
application structure.

\subsection{Top-Level Structure}
The executable entry point in `main.c` is intentionally minimal and delegates
control to the application layer in `app.c`. This top-level layer is
responsible for the overall execution flow, including mode selection, demo
execution, plaintext handling, and benchmark runs. Command-line parsing and
validation are centralized in `cli.c`, which keeps input handling separate from
the cryptographic part of the program.
The program currently supports two main execution modes. The first is a demo
mode intended for direct experiments with encryption and decryption. The second
is a benchmark mode, which repeatedly runs the selected scheme and records
timing data for later evaluation. This separation made it possible to keep the
interactive and experimental parts of the implementation independent.

\subsection{Scheme Abstraction}
At the core of the implementation is a small scheme abstraction defined in
`scheme.h`. Each cryptosystem variant is represented by a `SchemeOps`
structure containing function pointers for key generation, encryption,
decryption, and cleanup, together with a short identifier and a display name.
This provides a common interface for all implemented schemes while still
allowing each variant to keep its own internal data structures.
The currently implemented variants are the classical Merkle--Hellman scheme and
a permuted variant. Their implementations are placed in separate source files,
which keeps the code easier to read and compare. Scheme selection is handled in
`scheme.c`, where the requested identifier is resolved to the corresponding
implementation.

\subsection{Data Representation and Support Modules}
Messages are represented internally as bit vectors through the `BitView` and
`BitBuf` data structures. This matches the block-based nature of the knapsack
schemes and makes it straightforward to work with fixed-length binary message
blocks. For plaintext demonstrations, the helper logic converts text into bit
blocks before encryption and reconstructs the original text after decryption.
Several supporting modules are used around the core scheme implementations.
Seed handling and entropy acquisition are separated into `seed.c`, which allows
both deterministic runs and randomly initialized ones. Benchmarking is handled
in `bench.c`, where key generation, encryption, and decryption are measured
separately. Correctness is verified by checking that the decrypted output
matches the original message. In this way, the overall architecture remains
small, but still clearly separates cryptographic operations, application flow,
and experimental evaluation.
